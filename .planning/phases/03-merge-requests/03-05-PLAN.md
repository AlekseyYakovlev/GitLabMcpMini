## Phase Goal

**As a** автор агента AiAdventAgentV2, **I want to** через `gitlab-mcp.exe` вести Merge Request от просмотра до merge (список, детали, diff, комментарии, создание, правка, влитие), **so that** агент доводит свои изменения из Phase 2 до влитой ветки без ручной работы в GitLab.

<objective>
Final vertical slice: the agent merges an MR safely (MR-07). The GET pre-check reuses the shared status table from Plan 01. A single non-retried PUT follows, and GitLab refusals are explained in Russian. A stateful flow test then proves that the whole Phase 3 scenario chains together, and the tool set reaches 20.

Purpose: merge is the most irreversible operation. It must never run blind, never be retried silently, and never report a raw 405.
Output: `mr_merge.go`, merge rules in `errors.go`, `mr_merge_test.go`, `mr_flow_test.go`, 20-tool golden/e2e/smoke, ROADMAP note for 999.5.

OPEN QUESTION FOR THE AUTHOR (RESEARCH Open Question 1, not decided here): the handler already holds `mr.SHA` from the pre-check GET. Sending it as `sha` would close the race between the GET and the PUT and would satisfy a group "require SHA" setting. D-13 locks sha protection to v2 (MRX-03), so this plan does NOT send `sha` and maps the 400 "SHA must be provided" to a clear text instead. If the author approves an internal sha, it is a one-line change (`SHA: gitlab.Ptr(mr.SHA)`) plus a test. The SUMMARY must carry this question forward.

Resolution recorded (RESEARCH F6): the documented merge failures are 400/401/405/409/422. 406 is mapped defensively like 405, as D-14 requires.
</objective>
